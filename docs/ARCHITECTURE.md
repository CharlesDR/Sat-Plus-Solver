# Sat-Plus-Solver — Architecture

Status: **draft for review (rev 2: adds the world/factory-network layer)**. Scope: a client-side, two-layer planner driven by the Satisfactory Plus (SF+) dataset in `game_data.json`:

1. **World layer.** Factories and groups of factories, the links that carry items between them, and save-wide analytics: supply and demand, overproduction, flow of parts, power, and node usage. It plays the same role as satisfactory-factories.app or the Outposts in Satisfactory Modeler.
2. **Factory layer.** Each base-level factory is one solver run with satisfactory-tools parity: LP/MILP, alternates, objectives, a flowchart and a summary table.

Items marked **[A#]** are assumptions, collected in §10.

---

## 1. Decisions at a glance

| Area              | Decision                                                                                                                                                                                             | Why (short)                                                                                                                                                                   |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Layering          | **World → Groups (nestable) → Factories → Solver.** Links connect factories. Groups are organizational and aggregate their members.                                                                  | Matches how players build: separate sites, shipped between                                                                                                                    |
| World solve       | **Each factory is solved independently, with links as boundary conditions.** Links are either fixed-rate or _pull_, where the rate is whatever the consumer needs. Resolution runs consumers first.  | Every factory keeps its own objective stack. It's easy to understand and only changed factories re-solve. A joint optimization across all factories is in the backlog (§4.6). |
| Formulation       | LP over recipe rates plus node-usage variables, per factory. It becomes a MILP only when an objective needs integers.                                                                                | Handles cycles, byproducts and several producers per item directly                                                                                                            |
| Solver            | HiGHS compiled to WASM (`highs` npm), run in a Web Worker                                                                                                                                            | Fast, robust, has MILP, MIT license                                                                                                                                           |
| Scarce resource   | **Nodes per (resource, purity)** from `data/nodes.csv`. **One map-wide pool shared by all factories.**                                                                                               | Fluid modules and boosters make output per node non-linear in purity                                                                                                          |
| Extraction        | Modular Miner routes are **generated** from a rate model that assumes max output. Dataset rows are used to calibrate and cross-check it.                                                             | You asked for max output (Mk.3, full boosters)                                                                                                                                |
| Power             | Per-factory consumption **and generation**. Generator recipes produce a `MW` pseudo-item, so a power plant can be a factory with a MW target. The world totals everything on a single grid **[A8]**. | Lets you plan power across the whole save                                                                                                                                     |
| Data pipeline     | Build-time TS: raw JSON → parse → normalize → validate → `model.json`                                                                                                                                | One unit system; bad data fails the build                                                                                                                                     |
| Units             | items/min, fluids m³/min, power MW (positive = consumption, negative = generation)                                                                                                                   |                                                                                                                                                                               |
| Stack             | TypeScript, pnpm workspaces, Vite, React, Zustand, React Flow + ELK.js, TanStack Table, Vitest + fast-check                                                                                          | Details in §8                                                                                                                                                                 |
| Hosting / sharing | Static GitHub Pages. The whole save is a JSON document: autosaved locally, exportable and importable, and shared by URL when small enough.                                                           | No backend                                                                                                                                                                    |

Excluded by default (each with its reason in `overrides.json`, all listed in the build report): `Handgun` (building crafting), `Ficsmas`, FICSMAS Gift Tree, Doggo House (random loot), recipes using the `Placeholder` part, Well Water (its extractor draws 0 MW, so water would be free) **[A14]**, and pure sinks such as the Steam/Flue Gas Stacks (surplus is free disposal anyway). Geyser is ignored (no recipes). Space Elevator phases become virtual target items. The Alien Power Augmenter is modeled at its `BasePower` only **[A12]**. `IgnoreInputMultiplier` and `SpaceElevatorMultiplier` are ignored **[A2]**.

### 2.3 Extraction model

**Modular Miner.** The formula comes from the SF+-aware PioneerProductionPlanner (`SFPMinerRates`) and was calibrated against every fluid-module row in the dataset:

```
effective   = max(0.5, purity + (fluidBonus + boosterBonus) × processingMalus)
baseRate    = A_mk × 60 × effective                        (split evenly over 2 belt outputs)
output_k    = baseRate × perBase_k                         (per unit of base extraction, from the dataset's
                                                            Crusher/Smelter rows: e.g. Sand 4/3; Crushed X 1
                                                            + Crushed Gangue 1/3; Ingot 1 + Tailings Slurry 1/3)
fluidIn     = fluidBasePerMin × purity                     (not affected by boosters)
```

| Parameter         | Value used                                                                                                                                      | Source                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `purity`          | impure ½, normal 1, pure 2                                                                                                                      | MultiMachine `Capacities`                             |
| `A_mk`            | Mk.1 = 1, Mk.2 = 2, **Mk.3 = 4 (always used)**                                                                                                  | MultiMachine `PartsRatio` 60/120/240                  |
| `fluidBonus`      | Per (ore, fluid), from the dataset. Water 0.5, Muriatic 1.0, Slug Slime 2.5 (Kerr Crystal: 0.5), Energized Slime 2.5, Sulfuric 0.5, Nitric 1.0. | All 400+ fluid-module rows fit the formula            |
| `fluidBasePerMin` | 30 (Water, Sulfuric), 15 (Muriatic, Nitric, Energized Slime), Slug Slime 15 or 30 depending on ore                                              | Dataset                                               |
| `boosterBonus`    | **+3.0** (three booster slots, each full at +100%)                                                                                              | k-mods planner changelog v2.3                         |
| `processingMalus` | none 1.0, **Crusher 0.5**, **Smelter 0.5 [A3]**                                                                                                 | Crusher derived from the dataset's Fluid-Crusher rows |
| `perBase_k`       | From the dataset's Crusher/Smelter rows (e.g. Sand `1 1/3`); Sulfur Powder derived from the Fluid-Crusher rows                                  | Dataset                                               |
| Miner clock       | 100%. Boosters take the place of overclocking.                                                                                                  | Planner changelog v2.3                                |

Check: pure Montanion, Mk.3, Slug Slime → 4 × 60 × (2 + 2.5 + 3.0) = **1800/min = 900 on each belt** ✔ (unit test).

**Route generation.** For each ore, the generator produces routes over purity × processing (none, or a Crusher/Smelter product from the dataset) × fluid (none, or a dataset-listed fluid). The no-fluid option is dropped where the dataset has no plain route (Uranium, Kerr Crystal, Sulfur). Processing combined with fluid is allowed for every ore **[A4]**. Each route uses one node. That is 350 routes (only node classes with a count), replacing the ~420 dataset miner rows. The build cross-checks the model at 0 boosters against every one of the 379 dataset miner rows, exactly (rational arithmetic); a mismatch fails the build unless whitelisted. One known deviation is handled by an amount override: impure Sulfur Powder gangue **[A5]**. A Crusher/Smelter combined with a fluid uses the Fluid-Crusher machine's power **[A11]**.

**Other node-limited extractors** run at 250% clock, with power scaled by clock^`OverclockPowerExponent`:

| Resource                                          | Per node or site at max               | Basis                                                                                                                                    |
| ------------------------------------------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Crude Oil (Oil Extractor nodes)                   | 90 × purity × 2.5 → 112.5 / 225 / 450 | Dataset 1.5/s                                                                                                                            |
| Algal Mass                                        | 60 × 2.5 = 150                        | Dataset + MultiMachine                                                                                                                   |
| Toxic Air (Air Collector)                         | 90 × 2.5 = 225                        | Dataset 9 per 6 s                                                                                                                        |
| **Fracking site** (Nitrogen, Chlorine, Crude Oil) | **1500 m³/min per site** [A6]         | The N₂ benchmark: 13.33 normal-node-equivalents per cluster on average × 45 m³/min × 2.5. Can be overridden per resource in `nodes.csv`. |

**Unlimited resources** (Water, Air, Excited Photonic Matter) have no node constraint. Their extractor recipes stay in the LP, so their machines and power are counted, at 100% clock.

**Farming** needs no special handling. Seeds come only from Seed Extractors fed by Dirt, Peat or Loam, so crops are limited by soil nodes through ordinary item balance.

## 3. Factory layer: problem formulation

One factory means one `SolveRequest`, and one LP/MILP. Everything in this section is per factory.

### 3.1 Sets and variables

| Symbol        | Meaning                                                                                                                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| _R_           | Enabled recipes: dataset recipes after this factory's filters, plus generated extraction routes                                                                                                   |
| _I_           | Items, plus the pseudo-item **`MW`**. Generator recipes output `MW`. Machine draw stays in the power accounting and is **not** an `MW` input, so a factory never has to power itself.             |
| _N_           | Node classes (resource, purity) and fracking sites. Capacity `cap_n` is the map's node pool (§4.4).                                                                                               |
| `x_j ≥ 0`     | Machine count for recipe _j_. For a generated miner route, this is also its node usage.                                                                                                           |
| `s_i ≥ 0`     | **Import** of item _i_, `s_i ≤ importCap_i`. It comes from incoming links (§4) or from an unassigned import declared in this factory.                                                             |
| `z_i ≥ 0`     | Surplus of item _i_: byproducts and free disposal. At the world level, surplus is **available supply**.                                                                                           |
| `y_r ∈ {0,1}` | Whether resource type _r_ is used. MILP objectives only.                                                                                                                                          |
| `m_j ∈ ℤ≥0`   | Whole machines. In "whole machines" mode, and **always for heater recipes** (A17): there `x_j` is the boiler throughput in machine-equivalents and `m_j` the heaters built, which burn full fuel. |

### 3.2 Constraints

```
Item balance:     Σ_j a_ij·x_j + Σ_heaters h_ij·m_j + s_i − z_i = demand_i   ∀ i ∈ I
                  (heater-side flows h_ij of a heater recipe scale with m_j, its boiler pair with x_j; A17)
                  demand_i = target_i + Σ outgoing link rates of i   (from the world layer, §4.3)
Node capacity:    Σ_{j uses n} x_j ≤ cap_n                            ∀ n ∈ N
Resource limits:  Σ_{j extracts r} e_j·x_j ≤ limit_r                  ∀ r with a limit (A33; off = 0)
Imports:          0 ≤ s_i ≤ importCap_i                               (Σ incoming link rates + unassigned import)
Unique resources: Σ_{j uses r} x_j ≤ cap_r · y_r                      (MILP objectives only)
Whole machines:   x_j ≤ m_j                                            (optional; always for heaters: boiler ≤ heaters built)
Lexicographic:    f_k(x) ≤ f_k* + tol·max(|f_k*|, ε)                  for each objective already solved
```

**Byproducts.** Byproducts need no special handling. Surplus is free disposal, and every multi-output recipe feeds the balance of each output, so reuse happens automatically whenever it helps the objective. **Cycles** are just linear constraints. Build-time check: `max Σ outputs` with no nodes and no imports must be 0, otherwise there is a "free lunch" loop. Excited Photonic Matter from nothing is whitelisted.

### 3.3 Objectives

| #   | Objective                          | Expression                                                                                                                                                                              | Type      |
| --- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| O1  | Minimize raw resource use          | Σ_n NNE_n · usage_n, where NNE (normal-node-equivalent) is impure ½, normal 1, pure 2, and a fracking site counts at its NNE (13.33)                                                    | LP        |
| O2  | Minimize scarcity-weighted use     | Σ_r usageNNE_r × likely usage_r / **mapTotal**NNE_r (map-wide totals, not the factory budget; likely usage from `data/scarcity-usage.json`, default 1, A85). Weights can be overridden. | LP        |
| O3  | Minimize machines                  | Σ_j x_j, or Σ m_j in whole-machines mode **and for heaters always** (A17)                                                                                                               | LP / MILP |
| O4  | Minimize power                     | Σ_j max(powerMW_j, 0) · x_j: machine draw only, so generation never lowers it, except turbines (A16)                                                                                    | LP        |
| O5  | Maximize output given fixed inputs | max _t_, with target_i = _t_ · ratio_i. Bounded by imports, nodes and resource limits.                                                                                                  | LP        |
| O6  | Minimize unique raw resource types | Σ_r y_r                                                                                                                                                                                 | MILP      |

**Multi-priority.** Objectives are solved in order, each one fixed within a user tolerance before the next: **0.01% default, range 0.01%–90%**, with an absolute floor ε = 1e-6 (A15). The solver rejects a tolerance outside the range; the UI input clamps to it. A 1e-9 Σx regularizer picks a stable plan when there are ties.

**Scaling and pruning (A34).** Each stage's objective is scaled so its largest cost coefficient is 1 before it is solved or locked, because HiGHS's tolerances are absolute and O2's costs are around 1e-5 per machine; stage values and duals stay in natural units. After the last stage, a **prune pass** removes slivers: recipes running below the **minimum branch** (default **1% of a machine**, `minBranch`, 0 turns it off) are dropped and the last stage is re-solved on the plan's remaining recipes under the same lexicographic locks, then polished. Dropping them all is tried first (on the plan's own recipes, then on every recipe not yet dropped), then each alone in id order; a drop that makes the plan infeasible is undone, so a small branch the plan needs stays. Integer counts are fixed at the plan's values, so each re-solve is an LP (at most 24 per plan). The result lists the dropped recipes in `stats.pruned`.

**Flow prune (A68).** The prune pass must keep a sliver that an earlier stage's optimum leans on, so plans could still show tiny flows (a miner at 0.00007 machines fed 0.0005/min of acid). After it, every recipe with an input below the **minimum flow** (default **0.001/min**, `minFlow`, 0 turns it off) or with all its outputs below it, and every surplus or import below it, is held at 0 and the **whole stack is solved again** on the plan's own recipes, so each stage takes a fresh optimum without them. A drop is kept only when no stage ends up more than **1%** worse than the plan's (the first stage's LP relaxation turns most costly drops away with one LP), the plan adds no warning, and it has fewer tiny flows (no trading a tiny surplus for a tiny recipe that consumes it). All candidates together are tried first, then each alone in order (recipes by id, then surpluses, then imports); a flow the plan needs, such as a target below the minimum, stays. It repeats on the new plan, at most 6 attempts per plan. Recipes the plan no longer runs join `stats.pruned`.

**Simplicity (A73).** A lexicographic optimum can lean on tiny routes that save a fraction of a percent: the sample Frame Factory (Modular Frame 5/min, scarcity) ran 34 recipes, 15 of them below 1% of a machine, for 0.4% less scarcity than a 21-recipe plan. With `simplicity` on (the app's default; the solver's own default is off, so golden fixtures are unchanged), a pass between the prune pass and the flow prune drops **slivers** (recipes below `minBranch` machines, scaled down by the plan's largest recipe when it runs under one machine, so small targets keep their small steps) and then whole **recipe steps**, one at a time, smallest first, whenever doing without them costs at most **1% on every objective** against the first solve's plan. The flow prune shares that 1% cap. Every drop holds the recipe at 0 and re-solves the whole stack, so the returned plan is a fresh solution that passes the §3.5 checks; nothing is zeroed afterwards. Recipes below 1e-6 of the plan's largest, which exist only from rounding error, are dropped the same way whatever the setting, within the stack's own tolerance. **Steam into water (C1):** a conversion generator (a turbine making water or spent slime from a byproduct) is never pruned for its size, and the tidy step weighs it at 0.001 of a machine, so steam that would be dumped always becomes water when the plan uses water, at any rate, and never when the water would only be left over. **Byproduct farms (A86):** a recipe whose main (first) output nobody in the plan consumes and nothing wants, while another of its outputs is used, runs only for that byproduct (a recipe with nothing else used is disposal, not a farm). With simplicity and `farmCap` above 0 (the app passes 10%, `FARM_CAP`, 5% before 2026-10-15; the solver's default is 0, off), after the steps above the pass tries dropping each farm together with the recipes that only feed it (never miners or conversion generators), re-solving the stack on every recipe, and keeps a drop when every objective stays within `farmCap` of the first solve's plan (at most 4 tries). The slivers and steps then run again, holding their 1% against the farm-free plan; if the result has no fewer recipes than the plan with the farm, the farm stays.

**Miner fluids (A69).** `minerFluids` limits which optional fluid modules Modular Miner routes may use: `any` (the solver default), `water`, or `none`. In `none` an ore with no plain route keeps Water if its data allows it, otherwise its own fluids (Kerr Crystal and Uranium allow no Water); `water` likewise keeps an ore's own fluids only where it has neither a plain nor a Water route. With `minerFluidSupply: 'outside'` the fluid miner routes draw comes from a supply column of its own (`miner-supply:<fluid>`), used by miners only, that costs each m³ what making 60 m³/min of it standalone costs (its embodied cost, like a costed import); a fluid with no standalone plan is not offered and its routes are dropped. The plan reports the supply as an import of the fluid and lists it in `minerSupply`. `local` (default) makes it in the factory as before. World defaults carry both settings (v12); a new world supplies from outside, and an older save leaves them out, so it keeps fluid modules made here.

**Costing imports.** Imports are free by default. With the "cost imported inputs" toggle on, each `s_i` carries an **embodied cost** under this factory's objective stack:

- **Linked imports** use the **actual** per-unit cost of the upstream factory's solved plan: its marginal cost, the dual of the item's balance row with the plan's heater counts fixed (A18, A19).
- **Unassigned imports** use a standalone plan that produces _i_ **at the rate actually imported**, charged per unit as its cost ÷ that rate (A18). The plan is first solved with free imports, each import is costed at the rate it uses (1/min if none), and the plan is re-solved until the costs it was solved with match the costs at its own import rates. If that cycles, or after 4 rounds, the best plan seen is returned, re-costed at its own rates, with a warning. Standalone plans are cached per rate.
- For O6, an import brings in its embodied set of resource types.

### 3.4 Integer machine counts

The LP shows `x_j` and `ceil(x_j)`, with power reported on fractional counts. The "whole machines" toggle adds `m_j` and is only used by O3 and O6, with a 5 s limit. On timeout it returns the best solution found and its gap. Heater recipes always carry an integer `m_j` (A17), so a plan with an eligible heater is a MILP under the same limit. Every stage's plan is polished: an LP holds the stage objective at its value and minimizes Σx, so the tie-break applies at LP precision (a heater's boiler runs only as hard as needed, and a free capped import is not processed into surplus product, A32). A MILP plan is polished with its integer values fixed and 1e-10 relative room on the stage objective, and a plan whose counts fail at LP precision is re-solved with a 1e-10 MIP feasibility tolerance.

### 3.5 Failure modes

| Case                                    | Detection                                | What the user sees                                                                                                                                                          |
| --------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Target unreachable                      | Backward reachability before solving     | "Nothing can produce X", with the closest disabled recipes that would fix it                                                                                                |
| Infeasible                              | HiGHS status                             | Elastic re-solve. Reports the minimal relaxation: "needs 3.2 more pure Siterite nodes", "needs 30/min more Coal than its limit" or "needs 40/min more imported Steel Beam". |
| Unbounded                               | HiGHS status (O5 with unlimited sources) | Name the direction and ask for a cap. Sanity cap of 1e7/min.                                                                                                                |
| Numerical / lexicographic infeasibility | Status or residual > 1e-6                | Automatically retry with 10× tolerance and warn                                                                                                                             |
| MILP timeout                            | Time limit                               | Best solution found, plus its gap                                                                                                                                           |

## 4. World layer: factories, groups, links

### 4.1 Domain model

| Entity    | Fields                                                                                                                                                                                                                                                                                                                                                                                                                    | Notes                                                                                  |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `World`   | `factories[]`, `groups[]`, `links[]`, `defaults` (recipe toggles, objective stack, tolerance), `nodePool` (from `nodes.csv`, editable), `meta` (`v`, `dataHash`)                                                                                                                                                                                                                                                          | One per game save. This is the root of all state and of the share payload.             |
| `Group`   | `id`, `name`, `parentId?`, `collapsed`                                                                                                                                                                                                                                                                                                                                                                                    | Nestable folders. No solve semantics. Shown as one aggregated node in the outer graph. |
| `Factory` | `id`, `name`, `groupId?`, `request` (targets, objectives, tolerance, toggles that inherit `defaults` with per-factory overrides; recipe toggles are a per-recipe on/off map over the world's, plus a max-tier filter, A23), `unassignedImports[]`, `resources` (per raw resource: on/off and a max rate, A33), `priority`, `notes`, `tweaks[]` (A35), `manual?` (A36), `built?` (A44), `parentId?` and `collapsed?` (A49) | Leaf. Each one is solved by the factory layer.                                         |
| `Link`    | `id`, `from` (factory), `to` (factory), `item`, `mode` (`fixed` with a rate, or `pull`), `transport?` (`belt`, `pipe`, `train`, `truck`, `drone`, `unspecified`, plus a tier), `nested?` (A50)                                                                                                                                                                                                                            | Directed and single-item. Several links between the same pair are allowed.             |

In this model, a factory's **exports** are its targets plus its surplus `z`. A link can draw from either. Its **imports** are the incoming links plus any unassigned imports.

### 4.2 Link semantics

| Mode               | Effect on the consumer                                                                        | Effect on the producer     |
| ------------------ | --------------------------------------------------------------------------------------------- | -------------------------- |
| `fixed` (rate _q_) | `importCap_i += q`                                                                            | `demand_i += q`            |
| `pull`             | `importCap_i = ∞` from this link. The resolved rate _q_ is the consumer's actual `s_i` share. | `demand_i += q` (resolved) |

A link that draws on a producer's existing surplus without raising its demand is shown as "fed by surplus" when `q ≤ z_i` before linking. Either way the math is the same.

**Split targets and held builds [A92].** A target has two rates: **For links** and **Kept**. Links draw only on For links, so a producer makes `max(For links, Σ q) + Kept` of the item; Kept is never exported, and For links that no link takes is **spare** (surplus on the source, R7). A built factory under **Hold** (the default world setting) caps its pull links at its built For links rate, less its fixed links, shared by request; the excess is a short link and a world **shortfall**. Under **Grow** it adapts as any producer does.

### 4.3 World resolution algorithm

1. Build the factory dependency graph from links, and compute strongly connected components (SCCs) over the `pull` edges.
2. Solve the SCCs in **reverse topological order**, consumers first, so pull demand propagates upstream. `fixed` links impose no ordering.
3. For an SCC with more than one factory (a pull cycle), use fixed-point iteration: solve its members in turn, update the pull rates, and stop when every rate changes by less than 1e-6 relative. The limit is 25 iterations. If it doesn't converge, report the cycle and ask the user to make one of its links `fixed`.
4. Upstream infeasibility does **not** stop the world solve. The factory reports its diagnostic, and its outgoing links are marked **short** with the deficit.
5. **Parallel solves (S2).** Within a pass a factory starts once the factories it waits for (its pull consumers and sub-factories) have finished, with up to `concurrency` solves at once; the web app sends them to a pool of up to 4 workers (cores − 1). Results commit in the fixed solve order and identical requests share one solve, so the output is the same at any concurrency (tested at 1 and 4).
6. **Caching.** Each factory result is memoized by `hash(modelHash, effectiveRequest, resolvedLinkRates)`; the effective request carries the node pool and the resource limits. After an edit, only that factory and its upstream pull dependents re-solve.

### 4.4 Shared node pool

- `nodePool` is the map-wide count of nodes for each (resource, purity) and of fracking sites.
- Every factory may use up to the whole pool. The world ledger adds up usage across factories and **flags over-allocation** for each node class. That makes results deterministic and independent of order.
- **Resource limits** (A33) narrow one factory: one row per raw resource, whatever extracts it, with a checkbox to turn it off and, for node-limited resources, a maximum rate (items/min or m³/min). Unlimited resources (Water, Air, Excited Photonic Matter) only turn on and off. A helper, "allocate remaining", sets each limit to what the pool can extract minus what every other factory currently extracts.
- **[A9]** Strictly enforcing the map limit across factories would need the joint solve (§4.6). In v1 an over-allocation is a visible warning, not a constraint.

### 4.5 World analytics

| View                                      | Content                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Item ledger** (save-wide and per group) | For each item: produced, consumed, imported, exported, **surplus or available supply**, **unmet demand** (unassigned imports plus short links), and overproduction (surplus that no link takes)                                                                                                                                                                                                                                 |
| **Factory table**                         | Status (ok, infeasible, short), targets met, imports and exports, power draw and generation, nodes used, machine count                                                                                                                                                                                                                                                                                                          |
| **Link table**                            | Item, rate requested vs delivered, mode, transport. Belt or pipe count = `ceil(rate / capacity)`, using belt capacities from the dataset (60…1200/min). Pipe capacities are configurable **[A10]**.                                                                                                                                                                                                                             |
| **Power**                                 | Consumption and generation per factory and group, plus the save total. Net balance on the single grid **[A8]**. "Size power plant" sets a power factory's `MW` target to the current deficit.                                                                                                                                                                                                                                   |
| **Nodes**                                 | Map pool vs usage per (resource, purity), by factory, with over-allocation highlighted                                                                                                                                                                                                                                                                                                                                          |
| **Outer graph**                           | Factories and groups as nodes, with badges for status, power and nodes. Edges are links, grouped per factory pair and labeled by item and rate. Each card has one port per part it takes or ships; unmet imports are red input ports and surplus folds into a "…" port (A80). **Item trace:** pick an item to highlight every factory and link that touches it. A collapsed group shows only the flows that cross its boundary. |

**Group aggregation** is defined recursively: a group's ledger, power and node usage equal the sum over its descendants. Links between factories inside the same group are internal and are hidden when the group is collapsed.

### 4.6 Considered and deferred: joint world optimization

The alternative is one block LP over all factories, coupled by link-flow variables and a shared node-pool constraint. It would enforce map limits exactly and could choose where production happens. It is deferred because:

- per-factory objective stacks don't combine cleanly;
- it changes every factory whenever one edit is made;
- the model grows with the number of factories, and MILP objectives get much slower.

The backlog (PLAN M11) adds it as an opt-in "optimize world" action that reuses the same model builder in block form.

### 4.7 Manual factories

A factory in manual mode (A36) is not solved. Its plan is a list of recipe groups with fractional machine counts, frozen from the last solved plan and edited by hand (the frozen list plus an ordered edit list, which is also the undo history). World resolution computes it by arithmetic, in the factory's usual place in the solve order:

- Flows are count × per-machine rate. Heaters (A17) burn fuel and emit exhaust for ⌈count⌉ heaters; the boiler pair runs at the count.
- An item the plan consumes more of than it makes is imported. What its import caps (unassigned imports and incoming links, a pull link uncapped) do not cover is **missing**: drawn as Missing nodes, counted as unmet demand in the ledger, and reported as a `manual-short` warning.
- An item it makes more of than it consumes goes to its Kept targets first, then its outgoing links in id order, each up to what it asks, then its For links targets (A92); the rest is surplus. A link that gets less than it asks is short, so its consumer is short (§4.2 as for a failed producer).
- Power, node use and extraction follow the same arithmetic. Node use is fractional.

The result has the shape of a solve result, so ledgers, the flowchart and the tables need nothing new, but it is labelled "manual, not solver-checked": the solver's result checks (CLAUDE.md) apply to solves only. Linked import costs (A18) treat a manual producer as having no marginal cost, so its consumers fall back to standalone costing.

### 4.8 Build marks ("Matches in-game build")

A factory can be marked as built (A44): "Mark as built" stores a snapshot of its current plan in `Factory.built`. The snapshot holds the plan as recipe groups with fractional machine counts (the same entries manual mode freezes), the boundary flows at that moment (what it imported and what it delivered to targets and links), the data hash, the time it was marked, and fingerprints of the factory's own settings, the world defaults and its link boundary. Marking again replaces the snapshot; "Mark every factory as built" marks each factory that has a plan. Marking never changes the factory's mode.

Every world resolution checks each marked factory against its snapshot once the world is resolved, by arithmetic only:

- **Can it still run as built?** The built entries are run through the manual-mode arithmetic (§4.7) under today's request: today's targets and link demand, today's unassigned import caps, a fixed link capped at what it delivers, and a pull link uncapped unless its producer failed, is manual or is held (A92; then capped at what it delivers). A pull producer that is not held adapts to what it is asked, so its own flags, not its consumers', report whether it can.
- **Does today's plan match the build?** Today's recipe groups are compared with the built ones, as whole buildings when the factory plans whole machines and as fractional counts otherwise, within 1e-6 relative.

Each finding is one flag, worst first:

| Flag                  | Severity | Meaning                                                                                                    |
| --------------------- | -------- | ---------------------------------------------------------------------------------------------------------- |
| `inputs-short`        | error    | Can't get enough inputs: the built plan needs more of these items than its links and imports supply        |
| `needs-expansion`     | error    | The built plan makes less than its targets and links now ask for, per item                                 |
| `over-resource-limit` | error    | The built plan extracts more of a raw resource than the factory's limit now allows                         |
| `recipe-gone`         | error    | A built recipe is no longer in the game data                                                               |
| `plan-changed`        | warning  | Today's plan adds recipe groups or more machines than were built (needs rework), per recipe: built and now |
| `can-reduce`          | info     | Today's plan needs fewer machines, or drops recipe groups, and adds nothing                                |
| `data-changed`        | info     | The game data changed since the mark; recipe rates may have moved                                          |

A factory's build state is the worst severity: **matches** (no flags), **note** (info only), **differs** (a warning) or **can't run** (an error). Causes come from the fingerprints and data hash: the factory's own settings, the world defaults, its links, or the game data. A factory with a differing or broken build gets a `build-drift` world diagnostic. "Restore build" switches the factory to manual mode with the built entries as its frozen plan; "Re-mark as built" takes a new snapshot; "Clear mark" removes it.

### 4.9 Nested factories

A factory can sit inside another (A45, A49): `Factory.parentId` names its parent, to any depth and never in a cycle. Groups stay plain folders beside it. A sub-factory is still solved on its own; nesting only adds wiring, ordering and totals.

- **Wiring (A50).** Nesting a factory adds a pull link from it to its parent for each of its target items, marked `nested`; so does a new target item later. The links are ordinary links: editing one makes it the user's, and un-nesting removes only those still marked. What a sub-factory sends its parent counts toward its own target of that item, so it makes the larger of the two, not their sum.
- **Surplus (A51).** A parent may also draw on its sub-factories' surplus with no link: each sub-factory's leftover items (power aside) are extra import caps for the parent, drawn after fixed links and before pull links. A draw shows as a link result with mode `surplus` and id `surplus:<child>:<item>`. A parent comes after its sub-factories in the solve order, and their pull links put it first, so a family is a cycle the §4.3 sweep settles.
- **Totals (A52).** A parent's result carries its sub-factories, its totals with everything below it ("with sub-factories"), and the worst build state among the marked factories in its subtree.
- **Views (A53).** The view path holds the chain of parents, so Esc and the breadcrumb step back one level at a time. A parent's flowchart draws each sub-factory as one box, with what it sends and takes as lines to the parent's recipes; double-click opens it. The world canvas draws a parent with sub-factories as a frame around them, or, collapsed, as one node with only the flows crossing its subtree.

### 4.10 Modeler files

Satisfactory Modeler saves (`.sfmd`, M14, A37) are read and written by `@sps/world`; the solver worker runs both, since an import sizes the save with the LP and an export lays out flowcharts.

- **Sizing (A56).** Most nodes in a real Modeler save have no `Max`: Modeler sizes them from the flow. The import sizes them too, with one LP over the whole save (`sizeNetwork` in `@sps/solver`). Recipe nodes are machines, capped by their `Max`; a Dimensional Depot with a `Max` takes `Max` × its capacity; splitters, mergers and Outpost ports carry items through; resource nodes and unconnected inputs supply freely; sinks take anything. Three passes: capped machines as close to their cap as the wiring allows, then the least overflow on connected outputs (so a capped source's output is carried downstream), then the fewest uncapped machines. A node the passes leave at zero is listed in the report.
- **Import (A57).** One factory per Outpost, nested as the Outposts are (W2); a lone top-level Outpost with no nodes or ports of its own, a wrapper such as the export's "World", is unwrapped, and nodes outside every Outpost get a factory of their own. Each factory is in manual mode with its recipe nodes as the frozen plan (several nodes of one recipe add up), and is marked as built once the imported world resolves (A44). Items made in one factory and used in another, traced through logistics and ports, become pull links. A factory's targets are its net outputs less what the sized flows send to other factories (manual plans serve targets before links, A36); what it takes that no link brings becomes an uncapped unassigned import. Modular Miner rows, disposal stacks, unknown names and Modeler-only settings are listed in the report, and logistics nodes are counted there.
- **Export (A58, A59).** One factory is one Outpost; the world is one "World" Outpost holding an Outpost per factory, nested by parent and wired along the links, through the Outposts' ports when two factories sit in different Outposts. Each recipe group is a node named by its recipe, at its spot in our flowchart layout, with an input for each flowchart line; byproducts leave through output ports. Every recipe node carries our recipe and exact count in an extra `Sps` field, which the import reads back. The file is set to Modeler's Manual calculator, which solves one linear system: at each junction (belts, Splurgers and Outpost ports joining makers and takers of an item) what is made equals what is taken, and each `Max` fixes a count. So a `Max` goes only on the smallest set of nodes that fixes every other count (A59); a junction where several makers feed several takers meets at a Splurger, and a junction our plan leaves unbalanced (a manual plan) gets an Outpost port for the difference. Our own extractors (the miner model's routes) are written as Modeler's miner of the resource, counted in parts per minute; a fluid they take leaves through an output port, and a processed route's products come in through an input port.

| Option                           | Pros                                                                                          | Cons                                                       | Verdict       |
| -------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------- |
| **HiGHS via WASM** (`highs` npm) | Top-tier open-source LP/MILP, presolve, reliable status codes, MIT license, about 2.6 MB WASM | Large first download (lazy-loaded in a worker)             | **Chosen**    |
| javascript-lp-solver             | Tiny                                                                                          | Naive simplex, fragile numerics, weak MILP and diagnostics | Rejected      |
| glpk.js                          | Mature                                                                                        | GPL license, slower MILP                                   | Fallback only |
| Backend service                  | Any solver                                                                                    | Hosting, latency, and it breaks offline and static sharing | Not needed    |

**Performance.** One factory model is about 1.3k columns × 450 rows before pruning, and a few hundred after reverse-reachability pruning, which also lets self-sustaining breeding loops run from a starter **[A74]**. Expect 10–100 ms per lexicographic stage **[A7]**. A world of 30 factories cold-solves in about 3 s, and a single edit re-solves only the dirty factories. The solver runs in a Web Worker (a pool of 2, so independent SCCs solve in parallel).

The `LpBackend` interface (`solve(model, options) → {status, x, duals, objective}`) is injected, so tests run in Node against the same code.

## 6. Data pipeline

```
game_data.json ─┐
nodes.csv ──────┼─► parse (rationals) ─► normalize (per-min, signs, IDs, MultiMachine, MW pseudo-item)
miner-model.json┤        ─► generate extraction routes ─► validate ─► model.json + report.md
overrides.json ─┘                                              └─ build fails on any error
```

| Validation                                                           | Severity                 |
| -------------------------------------------------------------------- | ------------------------ |
| zod schema, parts referenced but undefined, unparseable numbers      | error                    |
| `nodes.csv` resources map to parts; counts are non-negative integers | error                    |
| Machines resolve; batch time > 0; fluid magnitude check              | error                    |
| Free-lunch loop LPs (§3.2), see below                                | error unless whitelisted |
| Generated routes differ from dataset rows at 0 boosters              | error unless whitelisted |
| Swapped power pair, unused parts, duplicate names                    | warning                  |

Output (`data/generated/`, git-ignored, built by `pnpm build:data` and in CI): `model.json` holds `items[]` (including `MW` and virtual targets), `machines[]`, `recipes[]` (node-limited extraction recipes carry `node`; generated miner routes carry `route`), `nodes[]` (id, resource, purity, map count, NNE), `beltCapacities[]` and `meta`; `report.md` is the human-readable build report.

**Free-lunch check.** Two LPs over recipes that have inputs and draw on no node, each recipe's activity ≤ 1 and every item's net ≥ 0: (1) maximize net item output with grid power available, (2) maximize net power with machine draw counted. A positive optimum fails the build. The data package cannot depend on the solver (§7), so the check is `findFreeLunch` in `@sps/solver` and `pnpm build:data` (`tooling/build-data.ts`) runs it after `buildModel`.

## 10. Risks, assumptions and open questions

Each row is one assumption, risk or decision, with its mitigation or default. Ids are stable; resolved and superseded rows move to `docs/archive/ARCHITECTURE-history.md` and keep a one-line stub here.

- **A1** Some variable-power recipes have `MinPower`/`AveragePower` swapped. _Mitigation:_ Use `AveragePower`; list them in the report.
- **A2** `IgnoreInputMultiplier` / `SpaceElevatorMultiplier` meaning unknown. _Mitigation:_ Ignored.
- **A3** Smelter malus assumed to be 0.5, like the Crusher. _Mitigation:_ One value in `miner-model.json`.
- **A4** Crusher/Smelter + fluid allowed for every ore. _Mitigation:_ Flag in `miner-model.json`.
- **A5** Impure Sulfur Powder gangue: 20 in the dataset vs 15 from the formula. _Mitigation:_ The dataset value wins.
- **A6** Fracking = 1500 m³/min per site. Actual Chlorine clusters are about 900; oil site counts differ (3 in the sheet vs 2 on the map). _Mitigation:_ Per-resource override in `nodes.csv`.
- **A7** Archived: History: measured in M2; current timings live in the benchmarks. See `docs/archive/ARCHITECTURE-history.md`.
- **A8** Single power grid for the whole save. _Mitigation:_ A per-factory `grid` tag in the backlog.
- **A9** The map node limit is checked across factories but not enforced. _Mitigation:_ Over-allocation warning, explicit budgets, joint solve in the backlog.
- **A10** Pipe capacities aren't in the dataset. _Mitigation:_ Configurable (defaults 300/600 m³/min).
- **A11** No Fluid-Smelter machine in the dataset; Smelter + fluid routes use the Fluid-Crusher machine's power. _Mitigation:_ One entry in `miner-model.json`.
- **A12** Alien Power Augmenter modeled as its 500 MW `BasePower`; its grid-wide percentage boost is not linear and is ignored. _Mitigation:_ `overrides.generatorOverrides`.
- **A13** Water, Crude Oil and Molten Tin are not flagged `Fluid` in the dataset. _Mitigation:_ `overrides.markAsFluid`.
- **A14** Well Water excluded: its extractor draws 0 MW in the dataset (pressurizer power is not attributed). _Mitigation:_ `overrides.excludeRecipes`.
- **A15** Lexicographic absolute floor ε = 1e-6, so an optimum of 0 still leaves room. _Mitigation:_ `LEX_EPSILON` in the solver.
- **A16** O4 never starts production to offset power. Turbines (steam → water, energized → spent slug slime) earn credit. _Mitigation:_ Only when O4 is not first, capped at the count the stage before runs.
- **A17** Heaters burn full fuel per machine: fuel and heater byproducts follow the rounded-up heater count; only the boiler side varies (Charles, 2026-10-01). _Mitigation:_ Heater classification in `overrides.json`; the build fails on an unclassified heater; the free-lunch check models the split.
- **A18** Embodied import cost is computed at the imported rate, not 1/min × rate, because heater fuel (and node limits) make cost a step function of rate (Charles, 2026-10-01). Linked-import duals (M5) come from the LP with heater counts fixed. _Mitigation:_ Re-cost until the costs match the plan's own import rates; on a cycle keep the best plan, costed at its own rates, with a warning.
- **A19** Linked-import cost (M5): per objective, the dual of the item's balance row in an LP of that objective alone, with every integer count fixed at the plan's value. Several links feeding one item are averaged by requested rate. _Mitigation:_ World passes repeat (at most 4) until the linked costs settle; otherwise the last pass is kept with a warning.
- **A20** A consumer's import of an item is split over its sources: fixed links first (by id, each up to its rate), then pull links in equal shares; unassigned imports supply what is left. _Mitigation:_ Deterministic; the pull share is the link's resolved rate. A held link (A92) is drawn on before the other pull links for its item.
- **A21** Links always add to the producer's demand (§4.2), so no link draws on surplus: all surplus is also overproduction. A fixed link ships its rate whatever the consumer draws; the unused part is the consumer's surplus. _Mitigation:_ The "fed by surplus" label (§4.2) is display-only, for the M8 link view. Since A92 links draw on a target's For links: For links no link takes is spare, which a link may take.
- **A22** A factory whose solve fails delivers nothing: its outgoing links are short by their full rate, and its own targets leave the ledger. Consumers are still solved as if their links deliver. _Mitigation:_ Factory status `short`; unmet demand in the ledger.
- **A23** Recipe tiers (M6): the dataset's `Tier` `"<major>-<minor>"` is ordered major first (`1-0` above `0-6`). `0-0` (428 recipes in SF+: 258 generated miner routes and 170 others, such as MAM and starting recipes) is read as no milestone, so the max-tier filter never removes it. The filter is a hard limit: an explicitly enabled recipe above it stays out. _Mitigation:_ `RecipeFilter.maxTier`; the recipe list shows "above tier".
- **A24** Flowchart edges (M7): the solve gives totals per item, not who feeds whom. Each item's producers (recipes in node order, then its import) fill its consumers (recipes, then target and byproduct) in turn, so every node conserves and an item gets at most producers + consumers − 1 edges. Edge rates are the plan's own per-recipe flows (`RecipeUsage.inputs`/`outputs`), so heater fuel and exhaust follow whole heaters and the boiler pair follows the boiler load (A17). _Mitigation:_ `allocate` in `packages/graph`; the split is a drawing choice, not a routing plan.
- **A25** Flowchart layout (M7): ELK runs in its own worker, not the solver worker (its bundled engine takes over a worker's `onmessage`). Node and label sizes are estimated from text length, not measured, and ELK runs with a fixed seed, so layout is deterministic. Brandes–Köpf node placement: network simplex took minutes on a 150-node plan. For readability (2026-10-02) node text and edge labels wrap to narrow columns (14 and 10 characters; node text 18 since A40) in a 14px font with tight spacing, and the factory flowchart spans 95% of the window width, as tall as its aspect ratio needs within 360px–80vh. _Mitigation:_ `layoutFactoryGraph(graph, engine)`; the engine is injected.
- **A26** World graph (M8): an expanded group is a frame around its members, a collapsed one a single node that takes its descendants' links; links inside one shown node are hidden. Edges are grouped per pair of shown nodes and labeled with each item's requested rate. Each shown factory or collapsed group gets an "Unmet imports" stub and an "Unclaimed surplus" stub from its own ledger (power excluded). Item trace marks a factory or collapsed group when any of its ledger flows for the item exceeds 1e-6/min, a link edge when it carries the item, and a stub when it lists it; frames are never marked. _Mitigation:_ `worldGraph` in `packages/graph`; laid out by ELK as compound nodes, like A25.
- **A27** Web app (M8): the worker resolves the whole world on every edit, memoizing factory solves across edits (at most 500 kept), so the factory view shows its factory as solved in the world, link demand and link imports included. New factory, group and link ids are `factory-n`, `group-n`, `link-n` with the smallest free `n`. Train, truck and drone links are labels only (no count, Q-M8-2); pipes keep the A10 capacities (Q-M8-1). _Mitigation:_ Transport calculators stay in M11.
- **A28** Saves (M9): `dataHash` is the model's `meta.dataHash`, which hashes the dataset, `nodes.csv`, `miner-model.json` and `overrides.json`, so an override edit also flags old saves. Local storage holds an autosave (written on every edit), one backup and up to 10 named slots; opening a share link, importing a file, loading a slot or restoring keeps the world it replaces as the backup. - **A90** Saved solver caches (Charles 2026-10-14, SV-3): timed first. With costed imports, import costing is most of a solve: Heavy Modular Frame 5/min importing three parts takes 2.3 s cold and 0.3 s with costs cached, against 0.14 s with free imports; Aluminum Casing 30/min 3.2 s cold, 3.0 s warm (its re-costing rounds re-solve the main plan), 0.9 s free. So the worker keeps its memo of factory solves (newest 100) and the solver's embodied import costs (newest 2 000, `costCacheEntries`/`seedCostCache`) in IndexedDB for the model's data hash, saved 2 s after the last solve and loaded when the worker starts; without storage it starts cold as before. Costs and plans are unchanged: only the cache outlives a reload. _Mitigation:_ A build-time unit-cost table to seed the costing rounds, and caching costs per unit rate when a plan is linear in rate, were not built: rounds re-solve the main plan and costs are step-shaped (A18), so neither is exact and the numbers above did not justify them.
- **A91** Suggested imports (Charles 2026-10-14, SV-4): `importSuggestions` reads a solved plan's graph: for each part one box makes and another uses (not a target, raw resource or import), its exclusive upstream is its makers, when they make nothing else the plan uses, and every box whose output goes only into that set.
